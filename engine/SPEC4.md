# SPEC4: ONE umbrella. One scheduler, one job adapter, one monitoring plane, one notification path, legacy retired in place

Builds on SPEC.md (runner contract/rules), SPEC2.md (public export, metrics ring, web), SPEC3.md (routine, spike manager, incidents/SLO, live monitor, reports).
SAME HARD RULES (see SPEC.md / SPEC3.md): Python 3.12 stdlib only on the runner side; NEVER mutate the live system while developing (no systemctl changes,
nothing under /etc,/usr,/var/lib,/var/log, no disabling/removing units, no moving/removing legacy scripts, no real notification sends); write only your owned files;
mutating paths tested with MOCKED runners and tmp dirs; list glue edits (cli.py, core.py, server.py, install.sh, etc/maint.toml, publish.py, routine.py, web/*) under `glue`.
No secrets in code, logs, or public files (the alert transports keep their credentials in ~ohmz/.hermes/alert_transports.env; never read, print or copy its values).

## 0. Goal and principles
The owner wants EVERYTHING maintained, monitored and reported from one place that can be extended later:
1. **One control plane.** `homelab-maint` owns scheduling (one tick), execution (one runner, one lock/concurrency model), state (one status.json + history + audit), alerting/reporting
   (one notification path and templates) and the website. Nothing else on the host schedules maintenance or sends maintenance/monitoring messages.
2. **Declarative.** Jobs, probes, notification routes, windows and classes live in TOML under /etc/homelab-maint/ (`jobs.toml`, `probes.toml`, `notify.toml`, `routine.toml`, `classes.toml`,
   `maint.toml`, `playbooks.toml`). Adding a thing = adding a table (or a small plugin file), never a new timer or cron line.
3. **Adapters first, ports second.** Critical legacy jobs (backups) keep their proven scripts but are SCHEDULED, GATED, LOGGED, ALERTED and REPORTED by the umbrella (adapter). Small scripts whose logic
   is simple and valuable are PORTED natively (parity-tested against the legacy script: same thresholds/semantics). Anything superseded is RETIRED.
4. **Retire in place, never rm.** Legacy units are disabled and legacy scripts are MOVED to `/usr/local/lib/homelab-maint/legacy/<name>/` with a README line and a rollback command; nothing is deleted.
   Cutover is per item, gated on a parity check, reversible with one command, and recorded in the change log and the maintenance journal.
5. **Distro/OS timers are observed, not replaced.** apt-daily(-upgrade), unattended-upgrades, logrotate, systemd-tmpfiles-clean, fstrim, man-db, e2scrub, snapd refresh, fwupd stay as OS services (security updates must
   keep working); the umbrella VERIFIES their last run/exit (`os_jobs` check), shows them in the routine/calendar as "managed externally" and alerts when they stop running. Same for always-on daemons that are
   not maintenance: sensor-exporter (fan supervisor; hardware control), glances, smartd, fail2ban, cloudflared, tailscale, docker, Plex, etc.: they are PROBED and their liveness is part of the monitoring plane.
6. **Same template everywhere.** Every message the umbrella sends (alerts, recoveries, maintenance updates, daily digest, weekly report) goes through ONE module (`notify.py`) that reuses the owner's
   existing Hermes transports (SMS carrier gateway + Gmail via `alert_transports`) and renders email in the SAME "Ohmz Cloud" HTML palette as the backup reports (`/usr/local/sbin/backup_report_html.py`
   is the reference renderer; add a maintenance renderer in the same style, importing its palette/helpers where possible). Root jobs call the Hermes code as user ohmz (`runuser -u ohmz --`),
   because it resolves its config through ~ohmz.
7. **Extensible by design.** Plugin points with auto-discovery: `homelab_maint/tasks/*.py` (checks/cleaners), `/etc/homelab-maint/plugins.d/*.py` (owner-written tasks, root-owned dir, same `@task` contract),
   `jobs.toml` (external commands), `probes.toml` (http/tcp/docker/command probes), notification channels in `notify.toml` (sms/email today; webhook/ntfy later), dashboard widgets (web registry).
   `homelab-maint new task|job|probe NAME` scaffolds from templates; `docs/EXTENDING.md` explains each with worked examples.

## 2. Streams, owners, files and contracts

### S7 unified notifications (owner `notify`): `homelab_maint/notify.py`, `homelab_maint/notify_templates.py`, `etc/notify.toml`, `tests/test_notify.py`
- API: `send(event: Event, cfg=None, now=None) -> Delivery` where `Event(kind, severity, title, summary, details=None, facts=None, status=None, dedupe_key=None, task=None)`; kinds:
  `alert` (warn/crit), `recovery`, `maintenance` (something was done: cleanup freed X, cutover, restart), `digest_daily`, `report_weekly`, `incident_open`, `incident_resolved`, `test`.
  Routes in `notify.toml` (`[routes]` per kind/severity -> channels sms/email/both/none, quiet hours only for non-critical, per-kind daily budgets, dedupe window, escalation: warn only emails until confirmed twice;
  crit = sms+email; recovery = sms short + email; maintenance = email only (+ sms when `facts.significant`); digest = email only).
- Delivery goes ONLY through the existing Hermes transports: call the Hermes code as user ohmz exactly like `backup-notify-hermes.py` does (reuse that script's calling convention or import `alert_transports` under runuser; do not copy credentials). Provide
  `render_email_html(event)` in the Ohmz Cloud palette consistent with `backup_report_html.py` (read it, import its palette/helpers when possible; fall back to plain text if rendering fails: an unreadable report beats none) with templates for each kind: header band with host + status colour,
  headline, summary, facts table, "what was done" list, "what to do" (playbook text for alerts), footer with a link line to https://maintenance.ohmzhomelab.ca (plain text only in SMS; links allowed in email).
- SMS builder: ASCII fold, one segment <= 130 chars, no URLs; prefix like `homelab: CRIT disk / 4% free`.
- Delivery log `STATE_DIR/notifications.jsonl` (`{"ts","kind","severity","title","channels":["sms","email"],"ok":bool,"note":short,"dedupe_key"}` no bodies, no addresses/phones) and `export() -> dict` for the website (`notifications.json`: last 100 + counts 24h/7d + failure count).
- Replace `core.Notifier._send` with `notify.send` via a small adapter (glue: lead edits core): the debounce state machine stays in core; delivery, templates, budgets and logging live here.
- `homelab-maint notify-test [kind]` (glue) sends one clearly labelled TEST of each requested kind; tests use a mocked transport (never send in tests).
- Weekly/daily digests: `digest_text` from reports.py (SPEC3 S5) feeds `digest_daily`/`report_weekly` emails (HTML summary + link). The routine decides when (08:30 daily digest only when something notable happened or every Monday; weekly report Sunday 09:00).

### S8 scheduler + external job adapter (owner `scheduler`): `homelab_maint/schedule.py`, `homelab_maint/scheduler.py`, `homelab_maint/jobs.py`, `etc/jobs.toml`, `tests/test_schedule.py`, `tests/test_scheduler.py`, `tests/test_jobs.py`, `systemd/homelab-maint-tick.service`, `systemd/homelab-maint-tick.timer`
- `schedule.py`: a stdlib cron-expression engine (5 fields + `@hourly/@daily/@weekly/@monthly`, names, ranges/steps/lists, `L`/`1st sat` helper via explicit `[monthly]` forms), timezone-correct (zoneinfo, host TZ; DST gaps/overlaps documented and tested), `next_after(expr, t)`, `prev_before`, jitter.
- `scheduler.py` + `homelab-maint tick` (glue: cli subcommand): run every minute by `homelab-maint-tick.timer` (Type=oneshot, Nice=10, flock so ticks never overlap); evaluates every enabled job/task (jobs.toml + registry tasks with cron `schedule` in maint.toml/routine.toml) and starts the due ones: persisted state per job (`STATE_DIR/sched.json`: last_start, last_end, last_rc, next_due, attempts, skipped_reason, running pid), catch-up after downtime (missed runs run once within `catchup_hours`, disruptive ones only inside their window), jitter, overlap prevention (a job never starts while its previous run is alive; stale locks detected by pid+start time), global concurrency (max N heavy jobs; `class` and `heavy=true` jobs serialised through one mutex so backups never overlap each other or a Plex-butler-window heavy task), admission control (do not START a P2/P3 job when pressure level >= 2, any `gates` busy, freeze window, or PAUSE; record `skipped_reason`, retry next tick up to `max_defer_hours`), retries with backoff for failures (max attempts/day), timeouts with TERM then KILL of the whole process group, runs as a configured user (`user="ohmz"` via `runuser -u` for Hermes/user scripts), output captured to `LOG_DIR/jobs/<name>/<ts>.log` (rotated, size-capped, secrets scrubbed), exit-code + optional success parser -> `Result`. The tick returns quickly (jobs run detached via a double-fork/`systemd-run --scope`-free subprocess group and are reaped on later ticks).
- `jobs.py`: the adapter. `jobs.toml` entries: `[[job]] name, title, command (argv list), user, schedule ("cron" or routine step), class (P0-P3), heavy, timeout_s, gates=[...], window, env, workdir, success = {exit_codes=[0], status_json="/var/log/backup/system-status.json", result_key="result", ok_values=["ok"], finished_key="finished", max_age_hours=...}, notify = {on_failure="alert", on_success="maintenance|none", detail_file="..."}, retire = "legacy-unit-name"`. Result mapping: ok/warn/crit/error with a one-line summary parsed from the status JSON or the last log line. Declare EVERY legacy job (backup-system, backup-immich, stack-backup, stack-watchdog, search-canary, prune-openwebui-media, bazarr-rules, tunarr-sync, docker-prune (until native parity), the smart hooks are event driven (see S9)) with their real commands and schedules read from the real units/crontab (verify each; do not guess). Jobs appear in status.json exactly like tasks (`klass` "J" for external jobs) and in the public export/calendar. Jobs that notify on their own (backup-notify) are marked `self_notifies=true` until migrated so nothing is sent twice; the migration plan lists when to turn that off.
- Provide `scheduler.explain(now) -> [{job,next_due,why}]` and `homelab-maint schedule` (glue) to print the unified schedule (the single place to see every routine). Tests: DST transitions, catch-up, overlap, stale lock, TERM/KILL, user switching (mocked), admission/defer, retries/backoff, jitter bounds, 1-minute tick performance (< 300 ms when nothing is due, measured read-only).

### S10 monitoring consolidation (owner `monitors`): `homelab_maint/probes.py`, `homelab_maint/tasks/monitors.py`, `etc/probes.toml`, `tests/test_probes.py`, `tests/test_monitors.py`

Cover, by reading the real sources (verify each): every Uptime Kuma monitor (read a COPY of the Kuma sqlite; list name/type/url/interval; port them, mark Plex's paused one as paused), every app container healthcheck state, the apps' local HTTP endpoints (Plex /identity, Immich ping, Kavita, Seerr, Open WebUI, Homarr, Nextcloud, Tunarr, Radarr, Sonarr, Prowlarr, Bazarr, Tautulli, SABnzbd, Deluge, Transmission, Glances 61208, sensor-exporter 9110, the maintenance site itself), infrastructure (docker daemon, cloudflared service + a public hostname probe if configured, tailscale, fail2ban (via `systemctl is-active` + log age), smartd, ollama :11434, ComfyUI when running), Hermes pieces (gateway/delivery timer liveness through their state files, not by importing Hermes), and the logic of `stack_watchdog.py` / `search_canary.py` / `health_alert.py` WITHOUT duplicating Hermes internals: run them as jobs (S8) and ingest their state/status files as `file_age|json` probes. `kuma_push_key` mapping so the umbrella can heartbeat Kuma push monitors (GET only on v1) if tokens exist; the umbrella also exposes its own dead-man's-switch heartbeat. ### S11 retirement, migration control and extensibility (owner `retire`): `homelab_maint/legacy.py`, `homelab_maint/scaffold.py`, `etc/legacy-retirement.toml`, `docs/EXTENDING.md`, `docs/MIGRATION.md`, `tests/test_legacy.py`, `tests/test_scaffold.py`
- `legacy-retirement.toml`: one `[[item]]` per legacy thing found by a REAL inventory (systemd units system+user, timers, cron, scripts in /usr/local/sbin and ~/ai-stack/scripts that were scheduled, hooks, drop-ins, notify wrappers): `name, kind (unit|timer|cron|script|hook), location, replaced_by (job/task/probe name), mode (adapter|port|retire|observe|keep), parity_check (command or task that must be green N times), retire_actions [disable unit, stop, move script to legacy dir, remove cron line], rollback_actions, owner_notes, depends_on`.
- `legacy.py` + CLI (glue) `homelab-maint migrate status|plan|check ITEM|cutover ITEM|rollback ITEM|journal`: `status` shows every legacy item, its replacement, parity state, retired or not; `check` runs the parity test (new thing healthy for N cycles, produced equivalent result, notification parity); `cutover` performs the ordered retire_actions via a mockable executor (disable timer, stop service, `mv` script into `/usr/local/lib/homelab-maint/legacy/<name>/` with a README, crontab line commented with a tag, drop-ins removed), records change log + maintenance journal + notification, refuses unless parity is green (or `--force` with reason), and is idempotent; `rollback` restores. Every action is `ctx.act`-style audited and honours PAUSE.
- Inventory must include things easy to miss: `backup-failure@.service` and `stack-alert@.service` OnFailure hooks, the immich-server-recycle gate drop-in, `launchpadlib-cache-clean`, anacron/cron.daily dpkg/apport/logrotate shims (observe), nvidia-cdi-refresh, tunarr-autostart, thermal-log, lmstudio.
- `scaffold.py` + CLI (glue) `homelab-maint new task|job|probe NAME`: generate a ready-to-edit file from templates (task module with test stub; jobs.toml snippet; probes.toml snippet), plugin discovery from `/etc/homelab-maint/plugins.d/*.py` (root-owned dir only: refuse group/world-writable files or dirs; import errors isolated: a broken plugin is reported as an `error` task and never breaks others). Provide the discovery helper (glue: cli.load_tasks calls it).
- `docs/EXTENDING.md`: how to add a check, a cleanup, an external job, a probe, a notification route/channel, a dashboard widget, a routine step; testing; safety checklist (class, protected list, caps, dry-run-first). `docs/MIGRATION.md`: the per-item cutover runbook generated from the TOML, with the order (observe-only items first, monitors, notifications, small jobs, backups last) and explicit "do not retire X until Y" rules, soak durations, rollback.
