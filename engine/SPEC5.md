# SPEC5: acknowledging known issues (email button + website button), 90-day suppression, acknowledged-issues register

Builds on SPEC.md (rules), SPEC3 (incidents/reports/live), SPEC4 (notify/scheduler), SPEC2/UI_CONTRACT (website). SAME HARD RULES: do NOT mutate the live system while developing (no systemctl changes, nothing under /etc,/usr,/var/lib,/var/log, no real notification sends); mutating logic tested with tmp dirs/mocks; Python 3.12 stdlib only; write only your owned files and list `glue`. Never put secrets, tokens (only hashes) or addresses/phones into public files, logs or exports.

## 1. What the owner asked
"Have an acknowledge button in the email and on the maintenance website with alerts, so I can say *I understand this error and I'm okay with it* and that exact error should not be notified again. Keep it as an acknowledged issue, but stop raising it as a red alert and stop sending emails about it for the next 90 days."

## 2. Semantics
- **The exact error** = a stable *fingerprint*: `fp = sha1(task + "|" + issue_key)[:16]`. `issue_key` comes from the task (`Result.issue_key`, optional new field, default None) else from `normalize(summary)` (lowercase; numbers, sizes, percentages, durations, times, hex/ids >= 8 chars, container ids replaced by `#`; whitespace collapsed; cut at 160 chars). Many existing summaries are volatile (top-N lists, percentages), so `etc/ack.toml` ships per-task key rules: `[key.<task>] mode = "text"|"task"|"regex"` with `regex = [...]` capture groups joined as the key (e.g. disk_forecast -> the mount names that are warn/crit; failed_units -> the sorted failed unit names; backup_freshness -> backup names; smart_trend -> device names; growth_watch -> the growing path; plex_media_mount_check/alert_path_health -> the failing condition; docker_df/memory_health/stuck_detector/orphan_report -> `task`). The builder derives these by READING every task's summary formats in homelab_maint/tasks/*.py and the live status.json produced in a scratch dir.
- **Severity ceiling.** An ack records the acknowledged severity (warn|crit). It suppresses the same fingerprint at that severity or lower. If the issue ESCALATES to a higher severity (warn -> crit) it is not suppressed and alerts once more (configurable `[ack] escalation_breaks = true`).
- **Severity policy.** `[ack] severities = ["warn"]` (shipped) decides WHICH severities may be acknowledged AT ALL. A critical issue (and a check whose own status is `error`) must keep alerting: it is never offered a button, never given an id or a token, and never accepted by the inbox or the CLI. Setting `["warn", "crit"]` restores critical acknowledgements (not recommended: it silences the loudest alert for the whole period; `escalation_breaks` still stops a warn ack from covering a later crit).
- **Duration.** Default 90 days (`[ack] days = 90`, per-ack override 1..365 via CLI/web). Expiry resumes normal alerting and sends ONE notice ("acknowledgement expired for X, still failing / no longer occurring").
- **Persistence.** The ack survives the problem clearing and recurring within the window (the same exact error will not page again), and survives restarts. It is stored in `STATE_DIR/acks.json` (atomic write + flock; schema below) and appended to `STATE_DIR/acks.jsonl` (audit trail of ack/unack/expire events).
- **Effect when acked** (runner side): Notifier does not send SMS/email for alert/recovery/incident kinds for that fingerprint (delivery log records `suppressed: acknowledged until <date>`); `status.json` entry keeps the true status but gets `acked: {fp, until, by, note, severity}` and `overall` excludes acked tasks (no red/yellow hero); incidents.py keeps the incident open in state `acknowledged` (stops escalation/paging, not resolved, still listed, MTTA recorded); reports list "acknowledged issues" with expiry dates and do not count them as open incidents in the health score deductions (but show them); SLO availability is NOT changed by acks (honesty); `live` ribbon shows them muted; `publish` exports `acks.json` for the website.
- **Un-acknowledge** (remove) is always possible (CLI/web); it restores normal alerting immediately.

## 3. Data
`STATE_DIR/acks.json` (0600): `{"v":1,"acks":{"<fp>":{"task","title","issue_key","summary" (redacted, <=200),"severity","acked_at":t,"until":t,"by":"email|web|cli","note":str<=200,"count_suppressed":n,"last_seen":t|null,"first_ack":t}},"tokens":{"<sha256(token)>":{"fp","task","severity","summary","issued_at","exp","used":false}}}`.
Public export `STATE_DIR/public/acks.json` (0644, no tokens/hashes): `{"generated_at","acks":[{"id":fp,"task","title","summary","severity","acked_at","until","days_left","by","note","suppressed":n,"active":bool (issue currently present)}],"stats":{"active":n,"expired_30d":n}}`.
Token hashes for the website's verify-only access: `STATE_DIR/ack/tokens.json` (0644, directory 0755; ONLY `{"<sha256(token)>":{"fp","exp","used":bool,"title","summary","severity"}}`; sha256 of a 256-bit random token cannot be inverted or forged).
Inbox (written by the web container, the ONLY write surface it has): `STATE_DIR/ack/inbox/` (dir mode 1730 root:10001 style, or 0770 with group 10001 — the packaging decides; files `<epoch_ms>-<8hex>.json`, <= 2 KB). Request schema: `{"v":1,"kind":"ack"|"unack","source":"email"|"web","token_hash":"…" (email),"fp":"…" (web/unack),"days":int,"note":str<=200,"severity":"warn|crit","ts":t,"sig":"hex"}` where `sig = HMAC-SHA256(key=STATE_DIR/ack/web.key, msg=canonical JSON without sig)` for source "web" (key readable by root and the container user only; created by install). The runner processes the inbox every minute (scheduler tick / check tier), validates strictly (schema, size, ts within +-10 min, known fp or token, signature, not used/expired, rate limit `max_acks_per_day = 50`), applies, deletes the file (invalid ones moved to `inbox/rejected/` with a reason, capped), and appends to acks.jsonl + audit.

## 4. Email button (owner `ack_notify`)
Alert emails (`alert`, `incident_open`, reminders, escalations) get: an HTML **"Acknowledge for 90 days"** button (table-based, bulletproof, same Ohmz Cloud palette) and a plain-text line `Acknowledge (90 days): <url>`; a muted line "You will stop receiving this exact alert; it stays listed as an acknowledged issue on the maintenance site."; the token URL `https://maintenance.ohmzhomelab.ca/ack/<token>` (base URL in `etc/notify.toml [ack] base_url`; token = 32 random bytes urlsafe-b64; stored ONLY as sha256 in acks.json/tokens.json; valid 30 days; single use; one fresh token per alert email, but the same fingerprint). **Never ack on GET** (mail scanners/prefetchers follow links): the URL opens a confirmation page on the website with the summary and a POST button; only the POST (with a one-time CSRF value embedded in that page) writes the inbox request. SMS carries no link. Recovery emails for an acked issue are suppressed. The expiry notice email explains how to re-acknowledge (a fresh button if it is still failing).

## 5. Website button (owner `ack_web`, runs AFTER the website v2 build finishes: it edits web/app.py and web/static/**)
The site stays read-only EXCEPT this one authenticated, rate-limited, CSRF-protected, audited path that only enqueues inbox files (no state writes, no docker.sock, no other mounts rw).
- Confirmation page `GET /ack/<token>` (static HTML+JS served by the app; the token is only read client-side from the path and sent in the POST body; page shows task, summary, severity, "this will silence this exact alert for N days") and `POST /api/ack/confirm` `{token, days?}`: backend hashes the token, looks it up in `ack/tokens.json`, checks exp/used, CSRF cookie+header double-submit, then writes an inbox request (source "email", token_hash). Response: "Received, applied within a minute".
- Website buttons for logged-in owner: every alert/incident/checks card with an acknowledgeable status (warn by default; a crit issue is never offered one) shows **Acknowledge** (days selector 7/30/90/365 + optional note) and an **Acknowledged issues** panel (from /api/acks) with Un-acknowledge. Auth for these write actions: `POST /api/ack/login {passphrase}` against a PBKDF2-hashed passphrase file (`ACK_PASSPHRASE_FILE`, created by the owner with a provided helper script `web/tools/set-ack-passphrase.py`), rate limited (5/min/IP-less global + exponential lockout), constant-time compare, session cookie (HttpOnly, SameSite=Strict, Secure, 12 h, HMAC-signed with a key file), CSRF double-submit on every write. If no passphrase is configured the buttons are hidden and only email-link acks work. Cloudflare Access in front remains the recommended outer layer (README).
- Writes: `POST /api/ack {fp, days, note, severity}` and `POST /api/unack {fp}` => HMAC-signed inbox requests as in section 3. The container mounts `STATE_DIR/ack/tokens.json` (via the directory `STATE_DIR/ack` with `inbox` rw and the rest ro) and `ack/web.key` ro; everything else unchanged and still `read_only: true`.
- Frontend: acknowledged items render muted (grey chip "Acknowledged until 12 Jan"), never red; hero/overall ignores them; Acknowledged-issues panel on the Health tab and a count chip in the nav; accessible dialog (focus trap, Esc), optimistic UI with "applied within a minute".
- /healthz unaffected.

## 8. AMENDMENT (owner request, supersedes the URL shape and flow in sections 4 and 5 where they differ)
**Email link = website URL carrying the error id, the token and the parameters**, and the site shows a confirmation page once the request is received:
`https://maintenance.ohmzhomelab.ca/ack?id=<fp>&t=<token>&d=<days>&s=<warn|crit>`
- `id` = the 16-hex issue fingerprint (also printed in the email as "Issue ID: <id>" for reference and for the CLI); `t` = the 43-char single-use token; `d` = days to silence (allowed set 7/30/90/365, default 90, capped by `[ack] max_days`, anything else is snapped/rejected); `s` = severity being acknowledged (the ceiling in section 2).
- Strict server-side validation of ALL parameters (charset/length/enum); the token's stored record binds fingerprint+severity+expiry, so `id`/`s` that do not match the token are rejected (defence in depth: a stolen link cannot be re-pointed at another issue; `d` can only lower or keep the default up to the cap, never extend beyond `max_days`).
- Flow: (1) GET `/ack?...` shows a **review-and-confirm page** (task title, plain-language summary, severity, since when it has been failing, "this silences this exact alert for 90 days; it stays listed as an acknowledged issue; a worse severity will still alert") with one clear button. The GET itself NEVER changes state (mail scanners/prefetchers follow links; an accidental 90-day silence of a real problem is the worst failure mode here). Optional `[ack] one_click = false` (default false): when true the page auto-submits after a visible 3-second countdown with a Cancel button, ONLY if the page was loaded with a same-origin, user-initiated navigation signal; document the risk.
  (2) The button POSTs `/api/ack/confirm {id, t, d, s, csrf}` (CSRF double-submit; no login needed because the token is the capability). The backend validates and writes the signed-less email inbox request (token-hash based, section 3), returns `202 {"state":"received","until":<predicted>,"issue":{title,summary,severity}}`.
  (3) The page immediately switches to a **confirmation view: "Received. This exact alert is silenced until <date>."**, shows the issue details, the Issue ID, what happens next, a link to the site's Health tab and to the Acknowledged-issues list, and then **polls `GET /api/ack/status?th=<first 16 hex of sha256(token)>`** (the page computes it with crypto.subtle; the server answers only `{state:"pending|applied|rejected|expired|unknown", until?, reason?}` from public data) every 3 s for up to 2 minutes, flipping the page to "Applied" (green check) when the runner has processed the inbox, or to a clear error ("This link was already used / has expired / is invalid") with next steps. Optional undo: the 202 response may include a one-time `undo` code valid for 15 minutes kept only in page memory; `POST /api/ack/undo {id, undo}` enqueues an unack.
- Already-used/expired/invalid/forged tokens render explicit, non-leaky error pages (same wording for unknown and wrong-binding tokens). Rate limit the confirm/status endpoints (global + per-token). Everything is logged (no tokens, only hashes) and counted in the audit trail.
- The notify side builds exactly this URL (token plaintext only in the email; hash only in storage), prints the Issue ID, and the plain-text part repeats the URL. Website acknowledge buttons for the logged-in owner keep section 5 (passphrase session) and also land on the same confirmation/applied view.
- Owners: `ack_web` owns the pages, endpoints, status polling and tests; `ack_notify` owns link building in notify.py/notify_templates.py (a later `ack_link_sync` step aligns it with this amendment if ack_notify built the earlier `/ack/<token>` shape).

### 8b. Website (logged-in) acknowledge = the same pipeline, confirmed IN PLACE (owner request)
No separate page: the alert card itself changes state.
- Each warn alert/check/incident card (Health, Live ribbon, Incidents, Maintenance) shows an **Acknowledge** control when the owner is logged in (otherwise a muted "Log in to acknowledge" hint; hidden entirely if no passphrase is configured). A crit issue gets no control at all: it must keep alerting (`[ack] severities`, section 2). Clicking opens a small inline popover (not a page): days selector 7/30/90/365 (default 90), optional note (<=200 chars), **Confirm** / Cancel. Keyboard accessible, focus trapped, Esc closes.
- On Confirm the card changes immediately (optimistic, announced via aria-live): red/amber status chip becomes a neutral grey **"Acknowledged — received…"** with a small spinner; the card moves out of the problems group into a collapsed "Acknowledged" group; the hero/overall health recomputes without it. Within ~1 minute the poll of `/api/ack/status` (same endpoint/semantics as the email flow, keyed by issue id) flips the chip to **"Acknowledged until <date>"** with a check mark, and the Acknowledged-issues panel/count chip in the nav updates. If the runner rejects it (or the request fails), the card reverts to its alert state with a clear inline error and a Retry button; nothing is ever left looking acknowledged when it is not.
- Acknowledged cards keep full details, show who/when/note, and offer **Un-acknowledge** (same inline popover pattern, instant revert to alert state after the runner applies it). Escalation to a higher severity visibly breaks the ack: the chip returns to red with "Escalated since acknowledgement".
- The email-link confirmation page (section 8) and this in-place UI share one status component and one client module (`web/static/ack.js`) so wording/states are identical: pending, applied, rejected, expired.
